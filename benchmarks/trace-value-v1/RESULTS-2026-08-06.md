# EchoEVM Trace Value Pilot — 2026-08-06

## Verdict

This 72-run frozen-evidence pilot does **not** show that the current full
`echoevm.trace.v1` JSON is better than a compact raw opcode trace for these
small bytecode diagnosis tasks.

All three conditions reached 100% semantic root-cause-and-fix accuracy. Under
the deliberately stricter consuming-opcode localization rule, control scored
22/24, EchoEVM 23/24, and raw opcode evidence 24/24. EchoEVM's +4.17 percentage
point delta over control has a task-clustered 95% bootstrap interval of
[-12.5, +25.0] points, so it is not a demonstrated improvement. EchoEVM also
used more evidence bytes and fresh tokens than either alternative.

The result is a useful negative baseline: the explainable schema is correct and
diagnosable, but its unfiltered full JSON is too verbose for tiny executions and
the task set is too easy to establish an accuracy advantage. The earlier
end-to-end Skill benchmark remains evidence for the broader EchoEVM workflow;
this experiment isolates the trace representation and should not inherit that
claim.

## Fixed design

- Eight bytecode tasks: calldata offset, DIV operand order, word alignment,
  return range, hash range, storage slot, revert rollback, and invalid jump.
- Three conditions: result-only control, Geth-style raw opcode logs, and full
  `echoevm.trace.v1` events.
- Three repetitions per task and condition, seeded randomized ordering, four
  concurrent workers.
- Same prompt, bytecode, calldata, model, reasoning level, answer schema, and
  hidden oracle in every condition; only `EVIDENCE.json` changes.
- Model `gpt-5.6-sol`, medium reasoning; Codex CLI 0.147.0-alpha.1.2.
- 72/72 Codex processes exited zero and 72/72 produced parseable answers.

## Aggregate results

| Metric | Control | Raw opcode | EchoEVM trace |
|---|---:|---:|---:|
| Semantic root-cause + fix | 24/24 | 24/24 | 24/24 |
| Strict consuming-op localization | 22/24 (91.67%) | 24/24 (100%) | 23/24 (95.83%) |
| Median score, /10 | 10 | 10 | 10 |
| Median duration | 30.91 s | 31.13 s | 33.25 s |
| Median fresh input + output tokens | 11,644 | 13,260.5 | 16,596.5 |
| Median output tokens | 731.5 | 680.5 | 679.5 |
| Median command calls | 2 | 2 | 2 |
| Median evidence bytes | 469 | 1,578.5 | 5,167 |

Relative to raw opcode evidence, EchoEVM used 25.16% more fresh tokens, took
6.80% longer by the descriptive medians, and supplied 227.34% more evidence
bytes. Output tokens were effectively equal (-0.15%). Relative to control,
EchoEVM used 42.53% more fresh tokens.

## Failure audit

The two strict control failures on `return_offset_shift` correctly identified
the root cause and fix but selected the `PUSH1` that introduced offset 1 rather
than the consuming `RETURN`. EchoEVM's one strict failure on
`keccak_length_31` similarly selected the `PUSH1` that introduced length 31
rather than `SHA3`. These are substantively correct causal diagnoses, which is
why semantic accuracy is reported separately and is 100% in every condition.

The raw and control 9/10 invalid-jump answers added the causally relevant
`PUSH1 5` as a secondary step where the strict oracle required no secondary.
They still count as correct diagnoses.

## Product finding discovered by the benchmark

Fixture generation found a real differential-conformance defect: after a
top-level `SSTORE` followed by `REVERT` or an exceptional halt, EchoEVM's
differential runner reported the provisional write as persistent state. The
runner now snapshots top-level execution and restores state on every non-success
status; dedicated revert and fault vectors prevent regression.

## Interpretation and next gate

Do not market this pilot as proof that explainable traces beat raw traces. The
next trace-value iteration should test longer compiled executions where state,
memory, nested frames, and bounded filtering matter, and compare a compact,
question-routed EchoEVM view rather than the full all-fields document. A positive
claim should require a confidence interval excluding zero or equal correctness
with at least 20% lower fresh-token use.

Auditable per-run results, answers, component scores, usage, and timings are in
`results/2026-08-06-pilot/runs.jsonl`; clustered analysis is in
